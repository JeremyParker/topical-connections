TOPICAL CONNECTIONS: PROJECT PLAN
Last updated: 25 November 2026


1. WHAT WE ARE BUILDING

A daily word-matching game. Each game shows 16 words that form 4 hidden sets
of 4. Words deliberately overlap between categories, so that a word may look
as though it belongs in more than one set.

There will be several versions of the game, each focused on a topic such as
music or biology. Each game mixes topical and non-topical content.

Games are generated by an algorithm from a graph of words and categories.
Contributors add to the graph and judge the generated games. Approved games
are queued, and one is served to the public per day. After playing, users see
who contributed to that game.


2. DECISIONS

Agreed:
  - React frontend and Python (FastAPI) backend.
  - Minimal deployment costs.
  - Topics are completely independent. Someone editing one topic is unaware
    that other topics exist.
  - Login is by emailed code, with no third-party authentication.
  - Stats are personal only. There are no public leaderboards.
  - We record which words were served, with which meaning, on which date, and
    the generator uses that history.
  - A word may be served two days in a row if its category is different.
  - Each topic has its own database. Topics start in one shared deployment
    and may eventually become separate deployments (section 4).
  - The first topic is music: music theory, instruments, music production,
    the popular music scene, clubs, producers, record labels, gear, etc.
  - The music game is called FourFour. The repo is topical-connections.
  - The is_topical flag is on categories, not words (section 6).

3. CODE STRUCTURE

One repo, one backend app and one frontend app. The generator is a separate
Python module, but not a separately deployed service.

  backend/app/         FastAPI: play, content, review, accounts
  backend/generator/   Pure Python: takes a graph, returns candidate games.
                       No database or web code.
  backend/migrations/  Alembic database migrations
  frontend/            Vite + React + TypeScript: the game, plus a content
                       area at /studio that loads only when needed
  tools/               One-off import of the existing words

Generation is an occasional batch job. When a contributor asks for new
candidates, the app queues a job row, and the same deployed image processes it.


4. HOSTING AND TOPICS

  React frontend   Cloudflare static assets    Free
  FastAPI          One 512 MB Fly machine      About $3-4/month
  Database         Neon Postgres               Free to start
  Email            Resend or Amazon SES        Expected to be cheap or free

Domain names are extra. Published Fly and Neon prices conflicted when checked
in November 2026, and email prices were not checked, so confirm all of them
before committing.

Neon's free compute allowance (most recently listed as 100 hours/month) will
not cover a database that is always awake. Cache the daily game at the CDN,
write to the database once per finished game, and budget for a paid tier if
traffic is steady.

All topics start in the same deployment. The hostname selects the database, and
branding and wording come from per-topic configuration.

  - No query can leak another topic's content by missing a topic filter.
  - User accounts are separate for each topic, even with the same email.
  - To add a topic: create a database, run migrations, and add a domain and
    a config entry.
  - To split a topic out later: deploy the same image configured with only
    that topic. Keep all topic settings in configuration, and never query
    across topic databases, so that this stays easy.
  - Tradeoffs: migrations run once per database, and topics share compute.


5. LOGIN

Playing does not require login. Anonymous stats stay in the browser and merge
into the account at first sign-in.

  - Codes have 6 digits, work once, expire after 10 minutes and allow 5
    attempts. Store an HMAC keyed with a server secret, not a plain hash.
  - Rate-limit requests per email and per IP. Respond identically whether or
    not the account exists.
  - Keep sessions for about 90 days. Put a random token in an HttpOnly,
    Secure, SameSite=Lax, host-only cookie and store only the token's hash.
  - Serve the API on the same site as the game, e.g. api.yourgame.com.
  - Set up SPF, DKIM and DMARC for each sending domain.
  - Roles are player, contributor and admin. Contributors are invited.


6. DATA MODEL

Each topic's database contains:

  users, login_codes, sessions
  words            Text, soft-delete flag
  categories       Name, notes, difficulty, is_topical
  links            Joins a word to a category: one meaning of the word.
                   Optional difficulty override and example sentence.
  contributions    Append-only: user, action, item, time
  candidates       Generated games awaiting review
  reviews          Contributor verdicts and feedback
  published_games  Unique serve date, status, snapshot
  game_entries     game_id, link_id, word_id, category_id
  plays            One per user per game

The is_topical flag: "bass" is topical as an instrument but not as a fish. Flagging
categories captures that difference. A word counts as topical if it belongs
to any topical category. This is derived, not stored on the word.

Snapshots: approving a game saves a full copy, so later edits cannot change
it. Credits come from contributions to the game's words, links and categories.

History: game_entries plus the serve date show which meaning of each word was
used and when. Links are soft-deleted so history survives, and changing a
link's meaning creates a new link.

Fixes compared with the old schema:
  - Categories need a difficulty field.
  - Links need a record of their author.
  - isDeleted defaulted to true and was never read.
  - The 3-character minimum blocked words such as "DJ".
  - Lowercasing everything lost proper names.


7. GAME GENERATOR

  1. Load the graph into memory, indexed by word and by category.
  2. Pick a seed category, then favor categories that share words with it.
     Sample randomly instead of trying every combination.
  3. Choose 4 words per category, preferring words that also fit other
     categories and so act as decoys.
  4. Require exactly one solution. Find every group of 4 words on the board
     that the graph allows, and reject the board unless exactly one set of
     4 groups covers all 16 words.
  5. Score overlap, topical mix, difficulty spread and freshness.

Reuse rules:
  Same word, same category        Minimum gap, then a strong penalty that
                                  fades over time
  Same word, different category   Allowed, even the next day
  Same category                   Moderate penalty (proposed)
  Decoy meaning                   Does not count as used

Queued games count as used on their scheduled date. Check for conflicts again
whenever a game is scheduled or moved.


8. CONTENT AND REVIEW

Content is the main constraint. A game uses 16 links, so the minimum number
of distinct links per topic with no repeated meanings is:

  30 days        480
  90 days      1,440
  1 year       5,840

The real numbers will be higher, because not every link will be usable.

Content entry must therefore be fast:
  - Paste many words into a category at once.
  - Autocomplete existing words and categories.
  - List categories that need more words.
  - List words with only one meaning.
  - Suggest links that would unlock the most new games.

Missing links can hide a second solution. Reviewers therefore play each
candidate blind before approving or rejecting it. A "this word also fits..."
button lets them add a missing link.


9. PUBLIC GAME

  - One game per day, with sharing through an emoji grid and other viral
    features to be defined.
  - The browser checks guesses. When the game ends it submits them, and the
    server recomputes and stores the result.
  - Personal stats and streaks only.
  - Contributor credits appear after the game.

11. BUILD ORDER

  1. Repo, schema, per-topic databases and email login
  2. Content studio, and import of the existing words
  3. Generator, tested on a synthetic graph while content grows
  4. Blind review and scheduling
  5. Public game, sharing, personal stats and contributor credits
  6. Second topic

Build steps 2 and 3 close together. The biggest risk is whether the graph is
dense enough to produce fun games.
